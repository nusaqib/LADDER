# IEC 61131-3 — the PLC software model (working notes)

> Normative source: IEC 61131-3 ed. 3.0 (2013), purchasable from IEC.
> Free practical companions: the matiec compiler sources, the PLCopen
> guidelines (plcopen.org). These notes are original summaries of the
> parts LADDER exercises.

## The software model

- **Configuration → Resource → Task → Program instance.** A configuration
  is one controller; resources are CPUs; tasks (cyclic, at an interval,
  or event-triggered) run program *instances*. Most single-CPU projects
  collapse this to one cyclic task running everything — LADDER's IEC
  backend emits exactly that (`CONFIGURATION`/`RESOURCE`/`TASK` +
  `PROGRAM ... WITH`).
- **POU kinds:** `FUNCTION` (stateless, returns a value, no internal
  state retained), `FUNCTION_BLOCK` (stateful, instantiated), `PROGRAM`
  (top-level FB, task-attachable). Timers/counters are FBs — every timer
  needs an *instance variable*.
- **Scan semantics:** inputs are sampled, the program executes top to
  bottom, outputs are written. Within one scan, a variable written early
  is visible to later logic (LADDER's simulator and lowering both honor
  this; the rung backends guard against reorderings that would break it).

## Data types

- Elementary: `BOOL`, `BYTE/WORD/DWORD/LWORD` (bit strings — no
  arithmetic ordering), `SINT/INT/DINT/LINT` (+ unsigned `U*`),
  `REAL/LREAL`, `TIME`, `DATE`, `TOD`, `DT`, `STRING/WSTRING`, `CHAR`.
- `TIME` literals: `T#500ms`, `T#1s`, `T#2m30s`, `T#1d2h`. Vendors
  normalize differently (Siemens shows `T#1S`, Rockwell stores TIMER.PRE
  as a DINT count of milliseconds) — LADDER parses `T#...` once at the
  IR layer and each backend renders natively.
- Derived: enumerations, subranges, `ARRAY [lo..hi] OF T`, `STRUCT`
  (LADDER UDTs lower to these). Initialization syntax:
  `x : INT := 5;`, arrays `:= [1, 2, 3]`.
- Located variables: `AT %IX0.0` (input bit), `%QW4` (output word),
  `%MD8` (memory dword). Size letters X/B/W/D/L; direction letters
  I/Q/M. IO maps feed these.

## The five languages — portability reality

| language | kind | portability in practice |
|---|---|---|
| ST (structured text) | textual | best; Pascal-like; the safest interchange |
| IL (instruction list) | textual | **deprecated in ed. 3**; accumulator model; keep to the simple subset (LD/ST/AND/OR/S/R/CAL) |
| LD (ladder) | graphic | universally *supported* but not universally *exchangeable* — the drawing is vendor XML/native |
| FBD (function block diagram) | graphic | as LD |
| SFC (sequential function chart) | structuring layer | steps/transitions/actions; textual form exists (STEP/TRANSITION/ACTION); action qualifiers N/S/R/P/L/D… |

Practical portability rules learned the hard way:

1. **ST expressions travel; graphics don't.** Exchange graphic bodies via
   PLCopen tc6 XML (see [plcopen-tc6-xml](plcopen-tc6-xml.md)), never by
   pretending a vendor drawing format is standard.
2. **IL formal calls** (`CAL fb(a := x, ...)`) have a stricter grammar
   than most references show — see [matiec](../tools/matiec.md).
3. **Edge detection** is an FB (`R_TRIG`/`F_TRIG`) in the standard; many
   vendors also have contact modifiers (|P|, |N|, ONS). LADDER lowers
   edges to explicit previous-value booleans instead, which renders
   identically everywhere and is visible to the model checker.
4. **Standard FBs you can rely on existing:** TON, TOF, TP, CTU, CTD,
   CTUD, R_TRIG, F_TRIG, SR, RS. (SR = set-dominant, RS =
   reset-dominant; safety logic wants reset-dominant → LADDER emits
   explicit `IF` latches rather than trusting the reader's memory.)

## Naming and identifiers

Identifiers: letters, digits, underscore; no leading digit; case
insensitive in the standard (treat as case-preserving but never rely on
case to distinguish). Keep to ASCII. Vendors add reserved words beyond
the standard's — avoid `Main`, `System`, single letters.

## What IEC 61131-3 does *not* cover

Hardware configuration, networking, safety qualification, HMI, alarms as
a first-class object, project file formats. Everything in that list is
vendor territory — which is precisely the gap LADDER's IR + iomaps +
backends bridge.
